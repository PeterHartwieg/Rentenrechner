## 2. Feld-Retention

**a** = Minimum im jeweiligen kurzen Screen (gegebenenfalls nur nach relevanter Auswahl); **b** = lokale progressive Details; **c** = klarer sekundärer Link zur genannten bestehenden Seite/Komponente; **d** = entfernt. Jede in einer Zelle einzeln benannte Eingabe erhält dieselbe Kategorie. Mehrfach vorhandene Zugänge sind gemeinsam erfasst, nicht die zugrunde liegenden Werte gelöscht. **Kein berechnungswirksamer Wert erhält d.** Ungeklärte Verdrahtung wird als c erhalten und als Integrationslücke benannt; c verspricht keinen heute fehlenden Combine-Editor.

## 3. Gewünschter Vertrag mit dem State Engineer

Vorschläge für **UI-Konsum**, keine beschlossene Schemaänderung. Opus liefert Typen, Adapter, Bounds, Readiness/Dauer, Mutation, Persistenz und Routing; Astra schreibt keine eigene Nettosumme, Statusmigration oder Rebase-Logik. Bestehende `ProductId`, `EvidenceState`, Domain- und Routen-Typen importieren. Insbesondere `versicherung` bleibt ProductId, `insurance` nur Workspace-Key. Folgende Namen sind Interface-Wünsche, keine Behauptung existierender Exporte.

```ts
type InputStatus = 'unknown' | 'assumed' | 'entered' | 'document';
type Field<T> = { value: T; status: Exclude<InputStatus, 'unknown'> }
  | { value: null; status: 'unknown'; previousValue?: T };
type ContextRef = { kind: 'plan' } | { kind: 'comparison'; id: string }
  | { kind: 'alternative'; id: string };
type EditorLink = { route: Route; search?: string; hash?: string;
  context: ContextRef; fieldId?: string; returnTo: Route; label: string };
type Reason = { code: string; message: string; editor: EditorLink };
type Readiness = { status: 'available' | 'estimated' | 'incomplete';
  reasons: readonly Reason[]; assumptions: readonly Reason[] };
type Calc<T> = { state: 'ready'; value: T; readiness: Readiness }
  | { state: 'pending' } | { state: 'error'; message: string; editor?: EditorLink };
type MoneyBasis = { kind: 'today' | 'retirement'; referenceYear: number;
  inflationRate: number; retirementAge: number; scopeLabel: string };
type SourceRef = { kind: 'statutory' } | { kind: 'instance'; instanceId: string };
type Duration = { source: SourceRef; status: InputStatus; editor?: EditorLink } & (
  { kind: 'lifelong' } | { kind: 'fixed'; years: number; endAge: number }
  | { kind: 'drawdown'; endAge: number; shared: true; affects: readonly SourceRef[] }
  | { kind: 'avd-plan'; endAge: number }
  | { kind: 'unknown' } | { kind: 'none'; reason: string });
type SourceRow = { source: SourceRef; productId?: ProductId; label: string;
  netMonthly: number | null; contribution: Field<number>; contributionLabel: string;
  provenanceLabel: string; duration: Duration; readiness: Readiness; editor: EditorLink };
type Summary = { netMonthly: number | null; basis: MoneyBasis;
  sources: readonly SourceRow[]; durationNotice?: string;
  target: null | { amount: number; basis: MoneyBasis; gap: number | null;
    nonComparableReason?: string } };
type UndoHandle = { id: string; label: string; available: boolean;
  unavailableReason?: string }; // opaque; keine UI-eigenen Snapshot-Restore-Closures
type MutationResult = { ok: true; undo?: UndoHandle }
  | { ok: false; kind: 'validation' | 'storage' | 'conflict'; reasons: readonly Reason[] };
type SaveState = { status: 'idle' | 'saving' | 'saved' | 'failed';
  savedAt?: string; message?: string };
```

`Summary.netMonthly=null` bei unvollständigem Gesamt-Netto; keine plausible Null als Fallback. Sichere einzelne Quellen nur anzeigen, wenn ihr Netto trotz fehlender Haushaltseingaben bestimmbar ist. Keine Summierung separat besteuerter Einzelresultate. MoneyBasis gilt gemeinsam für Hauptzahl, zugeordnete Quellen, Ziel und beide Alternativseiten. Ungültige Berechnung getrennt von „Angaben fehlen“ behandeln. Provenienzlabels aus erweitertem bestehendem Mapping; Statuscodes bleiben sprachneutral, Texte deutsch.

## 5. Offene Entscheidungen für den Lead

1. **Editor-Host und Rückweg:** Empfohlen: gemeinsame kompakte Formteile in Wizard und `AngabenProduktePage`; Plan öffnet gezielt diese Form, `/vertrag/:id` bleibt Ergebnisdetail. Legt Opus dafür Route/Query/Fragment mit Instanz, Kontext und Rückkehr fest oder einen routegebundenen Dialog? Alte Direktlinks dürfen keine ungespeicherten Änderungen übernehmen.
2. **Vergleich ohne Profil:** Vor Resultat dieselben kompakten Profildaten im Vergleichskontext abfragen, oder klar markierte Modellannahmen mit Readiness? Empfehlung: Eingaben wiederverwenden und fehlende Pflichtwerte gezielt ergänzen; niemals einen stillen Beispielmenschen als persönliche Berechnung zeigen. Wie wird Kopieren aus vorhandenem Plan ausdrücklich angeboten?
3. **PKV und Haushaltsscope:** Welche vorhandenen Felder bilden heutige KV/PPV, Ruhestandsprämie und weitere/Partner-Einkünfte tatsächlich ab? Liefert der aktuelle CombinedResult eine gesamte Haushaltsrente oder die erfassten Quellen einer Person unter Haushaltsbesteuerung? Scope vor „Gesamt“ verbindlich benennen; keine Nettozusage auf Basis einer unbekannten Prämie oder erfundenen Partnerdaten.
4. **bAV-Zuschuss:** Ein leicht verständliches Gesamtfeld braucht einen verlustfreien Adapter zu gesetzlich/prozentual/fix. Empfehlung bis dahin: knapper Zuschuss-Einstieg mit aufklappbarer bestehender Aufteilung. Welche Angaben sind je Durchführungsweg für Readiness zwingend?
5. **Sichtbare, bislang unwirksame Controls:** W-Dynamik (außer ETF), Riester-/AVD-Wizardkosten, synthetische ETF-Gebühren sowie Familienstand/Bundesland sind keine verlässlich persistierten Berechnungsinputs. Empfehlung: echte bestehende Felder verwenden, übrige c belassen und klar kennzeichnen; Lead entscheidet den begrenzten Integrationsumfang, keine stillen No-op-Regler ausliefern.
6. **Fehlende Instanzdetails:** Zeitrente-Dauer, mehrere Förder-/Garantie-/Steuerfelder und AVD-Payoutdetails sind teilweise nur im Compare-Editor vorhanden. Welche werden in 2B als echte Instanzfelder angeboten? c ist Erhalt des bestehenden Zugangs, kein Freibrief, einen Planvertrag über den Compare-Store zu ändern. Basisrente-Domain/zulässige Modes gegen widersprüchliche Kommentare abgleichen; Engine-Capabilities entscheiden, nicht pauschale UI-Copy.
7. **Ziel und Darstellung:** Empfehlung: Hauptdarstellung in heutigen Euro; explizites optionales Wunschziel ebenfalls. Legacy-Ziele können bisher anders verstanden worden sein: Status/Basis bei Migration konservativ halten. Wie wird nominale Detailansicht und nicht vergleichbare Zielbasis angezeigt?
8. **Undo/Persistenz:** Welche Lebensdauer hat Undo, bleibt es über Navigation erreichbar, wie werden zwischenzeitliche Änderungen und Transfers behandelt? Empfehlung: Handle bis Konflikt/Verbrauch sichtbar halten; keine Timeout-Annahme aus Mockup übernehmen. Auch gespeicherte Alternativen benötigen gesondertes Apply-Review nach Rebase.
9. **Demo und AVD-Verfügbarkeit:** Separate Demo ist optional; Empfehlung zunächst keine interaktive Demo, solange Isolation/Rückweg nicht eindeutig sind. AVD-Status-/Verfügbarkeitstext fachlich bestätigen lassen. Bestehende Produktunterstützung und Auswahl bleiben unabhängig davon erhalten.
